# Vision architecture and safety for a child-facing Visbot

## 1. Which vision mode fits this app and MVP?

### Takeaway
For a five-year-old's robot, the safest useful first release is **snapshot-on-demand**, initiated by an explicit child utterance/button and visibly acknowledged by the robot, with one compressed still sent through the app's existing Dify image-file path. Keep capture, upload, inference, and response as a bounded single request; do not begin with an always-on camera or movement-driving vision loop. Local detection can be added as a privacy-preserving enhancement, but it should not be treated as a general-purpose scene-understanding or safety system.

### Cited Findings
- Android recommends CameraX for most applications because it provides a higher-level API and resolves many device-compatibility issues; Camera2 is available from API 21 but requires handling device-specific configurations. This project targets an Android 8.1/API 27 robot, so a capability probe and native fallback remain important. — [Android: Choose a camera library](https://developer.android.com/training/camera/choose-camera-library); [Android Camera2](https://developer.android.com/media/camera/camera2)
- Google ML Kit object detection supports Android API 23+, can run in single-image or stream mode, detects/tracks up to five objects, and returns coarse categories rather than rich, reliable scene understanding. Its documentation says stream mode may need 30 or more frames before the first object is detected and recommends dropping frames/backpressure rather than queueing them. — [ML Kit object detection and tracking](https://developers.google.com/ml-kit/vision/object-detection/android)
- Dify's API documentation says application API calls should be made from a backend because a key embedded in a frontend/mobile client can be extracted and abused. The current repository's `DifyService` does make direct mobile HTTP calls, sends an image as a `local_file` upload reference, and identifies the end user using a device ID; this is an existing integration constraint and a credential/privacy risk to address before production child deployment. — [Dify API getting started](https://docs.dify.ai/en/getting-started/install-self-hosted/faq/api); [repository `lib/services/dify_service.dart`](https://github.com/tu-kimei/xiaozhi-android-client/blob/feat/visbot-next-phase/lib/services/dify_service.dart)
- Android requires camera permission at runtime on API 23+ and recommends asking in context, allowing cancellation, explaining the purpose, and gracefully degrading when permission is denied. — [Android runtime permissions](https://developer.android.com/training/permissions/requesting)
- Android Auto Backup includes most app-internal files and SharedPreferences by default for apps targeting API 23+, while cache and no-backup directories are excluded; Android documents explicit include/exclude rules and disabling backup for sensitive data. — [Android Auto Backup](https://developer.android.com/identity/data/autobackup)

### Inferences
- **Snapshot-on-demand:** lowest bandwidth and simplest consent story. A 1–2 MB JPEG (implementation target, not a sourced guarantee) sent only after a request is materially safer than continuous upload; latency is one capture + upload + cloud inference + Dify/Xiaozhi response round trip, so communicate “thinking” and time out rather than pretending to be real-time. The robot should answer “I cannot see that clearly” on timeout, blur, darkness, permission denial, offline state, or low confidence.
- **Periodic observation:** useful for an opt-in “look around” mode, but it multiplies bandwidth, cloud exposure, battery/thermal load, and accidental capture of other people. It should not be MVP. If later tested, use a low duty cycle (for example, one still every several seconds only while a parent-enabled session is visibly active), a bounded session duration, and discard frames immediately after inference.
- **Local detection:** best for cheap, fast, offline, privacy-preserving narrow signals such as “person/object present” or coarse obstacle cues. On API 27, ML Kit's API floor is compatible, but old ARMv7 hardware and vendor camera access must be measured. Local detections should be structured events, not raw images, and must never be advertised as reliable person identity, emotion, medical, or hazard recognition.
- **Cloud multimodal inference:** best semantic quality and easiest integration with the existing Dify upload path, but has variable latency, network dependence, data processor/retention exposure, and hallucination risk. It is appropriate for conversational “What is this?” snapshots, not for collision avoidance, autonomous navigation, or deciding whether a child is safe.
- The camera source should be abstracted (`CameraSource`) with integrated Camera2 first, API1 fallback, and optional UVC/vendor source. The existing hardware research found no reliable public proof that the exact Visbot camera is app-accessible; this must be a device probe, not an assumption. — [Project camera hardware notes](https://github.com/tu-kimei/xiaozhi-android-client/blob/feat/visbot-next-phase/research_notes/Visbot%20camera%20vision%20design/hardware-camera-stack.md)

### Gaps
- No reliable source gives Visbot-specific camera IDs, ownership, frame format, actual capture latency, CPU/thermal budget, or whether another vendor process already owns the camera. These require an on-device probe.
- No reliable source establishes Dify Cloud/self-hosted image retention, deletion SLA, or whether a particular configured Dify workflow forwards images to another model/provider. The deployment must obtain and document the selected provider's data-processing terms.

## 2. Privacy, consent, retention, failure behavior, and child safety

### Takeaway
Treat every camera frame containing a child or bystander as sensitive personal information. Make capture conspicuous and parent-controlled, collect only the one frame needed, do not retain raw frames locally or in conversation history by default, and provide a parent-visible “delete vision data” action that also requests server-side deletion where supported. Vision must be advisory and fail closed: uncertainty or failure means no movement and a calm verbal fallback, never an invented observation or a safety claim.

### Cited Findings
- COPPA applies to online services directed to children under 13, or services with actual knowledge they collect personal information online from children under 13. A five-year-old-facing service therefore needs a legal/privacy review, not merely a camera permission prompt. — [FTC COPPA rule overview](https://www.ftc.gov/legal-library/browse/rules/childrens-online-privacy-protection-rule-coppa)
- Android's permission guidance specifically recommends real-time awareness when accessing sensitive camera/microphone data and says denial should leave the rest of the app usable without pressure to change the decision. — [Android runtime permissions](https://developer.android.com/training/permissions/requesting)
- Android documents that app data is commonly backed up automatically and that developers can exclude sensitive files or disable backup. A raw captured image must therefore never be casually placed in ordinary files, databases, or SharedPreferences; use cache/no-backup storage and delete promptly, with backup rules reviewed for API 27 devices. — [Android Auto Backup](https://developer.android.com/identity/data/autobackup)
- Dify warns that API keys in client applications can be extracted. A mobile-embedded Dify key also makes it harder to enforce per-child quotas, revoke access, and guarantee that uploads are routed only through an approved service. — [Dify API getting started](https://docs.dify.ai/en/getting-started/install-self-hosted/faq/api)

### Inferences
- **Consent UX:** Parent enables “camera questions” in settings behind a parent gate; the app explains what is captured, where it is sent, whether it is retained, and how to delete it. At each child request, show a camera-active indicator/LED or on-screen banner and say aloud “I will take one picture to answer.” Do not capture on a wake word alone, in the background, or while the robot is docked/idle unless separately enabled.
- **Data minimization:** capture one low-resolution still; crop/resize locally; avoid audio-video recording; do not use face recognition, face embeddings, identity matching, emotion inference, or biometric templates. Send a narrowly scoped question plus image, not an entire conversation or device identifier where an ephemeral pseudonymous request ID suffices.
- **Retention/deletion contract:** default raw-frame retention is zero on device and zero in the app UI. Keep only a short-lived request state and a textual answer if the parent enables conversation history. Configure the Dify/provider side to disable logging/training where available, set the shortest documented TTL, and record the actual provider behavior. A “delete all vision data” control should clear local cache, uploaded-file IDs, related conversation entries, and invoke provider deletion APIs; if a provider cannot confirm deletion, disclose that limitation and avoid that provider for child images.
- **Failure behavior:** permission denied → continue voice/text conversation; camera unavailable or busy → say it cannot look right now; offline/timeout/5xx → no retry loop or queued image upload; corrupt/blurred/dark image → ask for help/reposition; low-confidence or ambiguous model answer → explicitly say “I’m not sure.” Never let a cloud answer directly invoke motion tools.
- **Child safety:** responses should avoid identifying strangers, inferring private attributes, or giving dangerous instructions. Add a post-inference policy gate for age-appropriate language and sensitive topics, but do not claim that an LLM safety filter is complete. Provide a parent override, audit event without raw image, and an emergency stop that disables all movement independently of vision/network state.
- **Movement guardrails:** vision may suggest a conversational answer or a non-actuating label only. MCP movement tools remain behind an independent safety controller: hard speed/duration caps, allowlisted commands, dead-man/stop command, obstacle/proximity sensors if available, no movement while uploading/inference is pending, and no movement from “person/edge/stairs/road” guesses. If any sensor, camera, MCP, network, or policy check fails, stop or remain stationary.

### Gaps
- COPPA applicability, parental-consent method, school/home deployment responsibilities, data-controller/processor roles, cross-border transfer, and age-appropriate design obligations depend on launch jurisdictions and the actual service operator; counsel must validate them.
- Provider-specific deletion, training-use, logging, and subprocessors cannot be inferred from Dify's generic API docs. Obtain the exact Dify host/model/provider terms and test deletion empirically.
- No source establishes that the Visbot has a hardware privacy shutter, camera LED, reliable obstacle sensors, or a safety-rated motion controller. These are acceptance-test items, not assumptions.

## 3. Recommended MVP and explicit non-goals

### Takeaway
Build a **parent-enabled, one-shot “look and answer” flow**: capability probe → explicit request → visible capture → local resize/redaction if feasible → one Dify upload through a server-side relay → bounded multimodal answer → discard raw image → no motion side effect. Ship diagnostics and safety fallbacks before adding periodic or autonomous vision.

### Cited Findings
- CameraX is the recommended high-level Android camera API and supports Android 5.0+, so it is a reasonable UI-layer candidate after confirming the Visbot exposes a normal Android camera; Camera2/API1 fallback is needed for vendor quirks. — [Android: Choose a camera library](https://developer.android.com/training/camera/choose-camera-library)
- ML Kit's single-image mode is intended for static images and has potentially higher latency than stream mode, while stream mode is optimized for low-latency tracking and can produce partial/initial results. This supports using single-image inference for MVP conversation and reserving stream mode for a separately justified local detector. — [ML Kit object detection and tracking](https://developers.google.com/ml-kit/vision/object-detection/android)
- Android recommends graceful degradation when permission is denied, directly supporting a voice-only fallback. — [Android runtime permissions](https://developer.android.com/training/permissions/requesting)
- Dify documents that frontend/client API keys are extractable, supporting a small authenticated relay rather than shipping the Dify secret in the APK. — [Dify API getting started](https://docs.dify.ai/en/getting-started/install-self-hosted/faq/api)

### Inferences
- **MVP components:**
  1. `CameraSource` capability probe and diagnostics (IDs, permissions, supported sizes, open/configure result, lifecycle errors); start with a small JPEG and no continuous preview if hardware allows.
  2. Flutter “Look” action plus voice intent, parent gate, consent copy, active-capture indicator, cancel button, and camera-denied fallback.
  3. `VisionRequest` with request ID, timestamp, one image, and child-safe question; enforce one in-flight request, size/time limits, no offline queue, and cancellation.
  4. A server-side relay that authenticates the robot/device, stores no raw images, calls Dify, strips provider identifiers, applies response policy, and returns a bounded answer. If a relay is impossible for a prototype, clearly mark the embedded-key path as non-production and rate-limit/revoke aggressively.
  5. Local cleanup in `finally`: close image buffers, delete temporary files, clear upload IDs where the API supports it; keep no raw-frame thumbnails in logs or crash reports. Exclude any unavoidable temporary directory from Android backup.
  6. Response contract: answer, confidence/uncertainty phrase, failure code, and `canMove=false` always for MVP. MCP tools are not called from the vision response.
  7. Acceptance tests: permission denial, camera busy, no camera, rotated/low-light/blurred frame, offline, timeout, Dify 4xx/5xx, process kill during upload, duplicate request, parent disable/delete, and attempted prompt injection in an image.
- **Explicit non-goals for MVP:** continuous video streaming; periodic/background observation; autonomous navigation or obstacle avoidance; safety-critical detection; face recognition or identification; emotion/gaze/age/gender/race/health inference; persistent child profile built from images; cloud image gallery; model training on child images; automatic camera activation; direct vision-to-MCP movement; guaranteed semantic accuracy; and treating a single model answer as proof that a room, person, toy, stair, road, or animal is safe.
- **Phase gates:** only consider local periodic observation after measuring battery/thermal/CPU, false positives/negatives, and parent comprehension; only consider cloud continuous vision after a documented retention/DPA review and explicit session controls; only consider vision-assisted movement after an independent robotics safety review and sensor/controller evidence, not merely a better multimodal model.

### Gaps
- Exact latency, image-size/bandwidth budget, and acceptable answer delay need measurement on the Visbot's Android 8.1/ARMv7 hardware and network. Do not promise numerical targets until instrumented.
- The repository's current Dify implementation persists conversation-ID mappings in SharedPreferences and logs request metadata; a production privacy pass should verify that no image IDs, API keys, child text, or device identifiers enter logs/backups, and should define migration/deletion behavior. — [repository `lib/services/dify_service.dart`](https://github.com/tu-kimei/xiaozhi-android-client/blob/feat/visbot-next-phase/lib/services/dify_service.dart)
